## 1️⃣ Task List מפורט – מה בדיוק עושים

### 🎯 מטרה על

להוציא את לוגיקת **flow selection + approval + ביצוע טרייד** מתוך ה־routes
ולהעביר אותה למודול מרכזי `ExecutionBot`, כך שכל המקורות (HTTP, טלגרם, future agents) יקראו למקום אחד:

* `/trade/execute`
* `/trade/approve`
* `/telegram/...`
* Auto Executor / n8n / Agents

כולם → `execution_bot.open_position(...)`.

---

### שלב 1 – יצירת מודול Execution Bot (Controller)

📁 קובץ חדש: `utils/execution_bot.py`

בפנים להגדיר מחלקה, לדוגמה:

```python
class ExecutionBot:
    def __init__(self, logger: logging.Logger | None = None):
        ...

    async def open_position(self, ticket_exec: dict, *, source: str = "api") -> dict:
        ...

    async def close_position(self, position_id: str | None = None, symbol: str | None = None, reason: str = "") -> dict:
        ...

    async def manage_once(self) -> dict:
        ...
```

#### מה נכנס ל־`open_position`:

1. **Flow selection (היום ב־/execute ו-/approve):**

   * בחירה בין:

     * `MARKET` / `HYBRID` / מצב אחר (איך שזה היום במערכת שלך)
   * כל הלוגיקה:

     * "אם צריך אישור → HYBRID"
     * "אם כבר אושר → MARKET"
     * טיפול ב־spec flow (smart/hybrid וכו’)

2. **Approval gating:**

   * אם הטרייד דורש אישור → לא לבצע מיד, אלא:

     * להכניס ל־Confirm Store / Redis / מה שיש היום
     * להחזיר סטטוס `"pending_approval"`
   * אם הקריאה היא מתוך `/approve` / טלגרם → `open_position` יקבל flag מתאים (`source="telegram"` / `"approval"`) ויידע לדלג על ה־approval gate ולבצע בפועל.

3. **בניית `ticket_exec` (payload לביצוע):**

   * כל לוגיקת הבנייה:

     * `symbol`, `side`, `position_type`, `leverage`, `budget/quantity`
     * SL/TP (או פרמטרים לחישוב)
     * metadata: source, request_id, quality_score, וכו’
   * היום זה מפוזר בתוך `/execute` ו־`/approve` – צריך לעבור פנימה ל־ExecutionBot.

4. **קריאה ללוגיקת ביצוע הקיימת:**

   * במקום שה־routes יקראו ישירות ל־`_execute_trade_direct` / `_execute_trade_hybrid` / `execute_trade_live`,
   * ה־ExecutionBot:

     * יחליט איזה flow (MARKET/HYBRID/…)
     * יקרא לפונקציה המתאימה מתוך `trade_executor.py`
   * את הפונקציות `_execute_trade_direct` / `_execute_trade_hybrid`:

     * להעביר *פנימה* ל־`execution_bot.py`
     * או להשאיר ב־`trade_executor.py` אבל שלא יהיו private ל־routes, אלא ל־ExecutionBot בלבד.

5. **Handling של שגיאות מיוחדות (כמו -4061):**

   * כל הטיפול בבאגים של Binance (למשל Hedge/OneWay, Order would trigger immediately וכו’)
   * במקום להיות כתוב כמה פעמים ב־routes → לרכז אותו ב־ExecutionBot.

6. **Response אחיד:**

   * להחזיר dict מסודר, לדוגמה:

   ```json
   {
     "status": "opened" | "pending_approval" | "rejected" | "error",
     "flow": "MARKET" | "HYBRID",
     "symbol": "BTCUSDT",
     "side": "LONG",
     "position_id": "...",
     "entry_orders": [...],
     "sl_order": "...",
     "tp_orders": [...],
     "reason": "..."
   }
   ```

### שלב 2 – דילול routes: להפוך אותם ל-Thin

#### `/trade/execute`

* להוריד ממנו:

  * Flow selection
  * Approval logic
  * Payload building
  * Retry logic
* להשאיר:

  * ולידציה בסיסית של request (Pydantic model)
  * מיפוי request → ticket_exec (אם צריך)
  * קריאה אחת:

    ```python
    res = await execution_bot.open_position(ticket_exec, source="api")
    return JSONResponse(res)
    ```

#### `/trade/approve`

* במקום לשכפל את הלוגיקה:

  * לקבל `ticket_id` / `request_id`
  * להביא את ה־ticket מה־ConfirmStore/Redis (כמו היום)
  * להעביר ל־ExecutionBot:

    ```python
    res = await execution_bot.open_position(ticket_exec, source="approval")
    return JSONResponse(res)
    ```

> הרעיון: **שתי** ה־routes האלה עושים אותו דבר: "תבצע את הטרייד" – רק בקונטקסט אחר (`api` vs `approval`). את ההבדל מנהלים ב־ExecutionBot, לא ב־routes.

### שלב 3 – חיבור לטלגרם / Auto Executor / עתיד

1. כל מקום בטלגרם שקורא היום ל־`execute_trade_live` / ל־routes במיוחד:

   * אם יש לוגיקה שמבצעת טרייד "בעקיפין" – להעביר אותה לשימוש ב־ExecutionBot (או דרך route שמדבר עם ExecutionBot).

2. Auto Executor:

   * פתיחה: אם יש מנגנון שפותח פוזיציות אוטומטית (כשעובר quality gate וכו’) –
     לוודא שגם הוא משתמש ב־ExecutionBot ולא קורא פנימה ל־`trade_executor.py` ישירות במקביל.

3. n8n / future agents:

   * מעכשיו, כשיוספו – הם תמיד ידברו או:

     * עם route אחד `/trade/execute` (thin),
     * או ישירות עם ExecutionBot ברמת קוד.

### שלב 4 – בדיקות וקריטריונים להצלחה

* `/trade/execute`:

  * ממשיך לעבוד אותו דבר מבחינת Response ללקוח.
  * ההתנהגות בפועל זהה, רק שהקוד פנימית נקי יותר.

* `/trade/approve`:

  * אותו Flow של hybrid/approval → אבל בלי לוגיקה כפולה.

* טלגרם:

  * `/approve` לא נשבר, אישור טריידים עובד כרגיל.

* לוגים:

  * לוודא שאין שינויים קיצוניים בפורמט (כדי לא לשבור ניטור),
  * אבל כן אפשר להוסיף לוג מרוכז ב־ExecutionBot בסגנון:

    * "open_position: source=api/hybrid, flow=HYBRID, symbol=..., side=..., status=opened"
